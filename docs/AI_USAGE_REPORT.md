# Mandatory AI Usage Report

**AI TOOL USED:** Cursor with Grok

## WHAT I ASKED AI TO DO

Help break the assignment into an implementation plan and organize the development steps.

Assist with application implementation, including backend/API patterns, frontend components, validation logic, debugging, and repetitive code.

Help review and prepare technical documentation and validation notes as the implementation evolved.

## PROMPT THAT WAS MOST USEFUL

“Analyze the assignment brief and create a step-by-step product engineering plan covering requirements, user roles, workflows, architecture, database design, API design, implementation, validation, and submission documentation. Keep the implementation and documentation aligned throughout the development process, and identify what should be reviewed or updated at each stage.”

## CODE GENERATED BY AI: What part?

AI-assisted implementation was used for parts of the backend and frontend, including API/controller/service patterns, React components, form/validation handling, UI structure, and repetitive implementation code. I reviewed and integrated the generated suggestions into the existing application rather than treating the output as final without validation.

## CODE MODIFIED: What part?

I modified and reviewed the generated implementation wherever it needed to match the product rules and actual application behavior. This included ticket workflow and status transitions, SLA handling, escalation behavior, authorization boundaries, internal/public comments, resolution and reopen logic, dashboard behavior, and UI validation.

## AI OUTPUT THAT WAS WRONG

An earlier AI-assisted design included assumptions that did not match the final product decisions, including a business-hours SLA approach and automatic reassignment/escalation behavior on breach. Some documentation also continued to describe earlier or unimplemented behavior after the implementation had evolved.

## HOW I IDENTIFIED THE PROBLEM

I compared the proposed behavior with the assignment requirements and the product workflow I had defined. I also checked the implementation through server tests, builds, API behavior, and manual browser validation. During the final documentation audit, I compared the documented behavior with the actual running application and found places where the documentation no longer matched the implementation.

## HOW I FIXED IT

I changed the SLA model to deterministic wall-clock time:

- Critical — 4 hours
- High — 8 hours
- Medium — 24 hours
- Low — 48 hours

PENDING does not pause the SLA clock. SLA status is kept separate from the operational ticket status, and escalation is handled explicitly rather than automatically reassigning the ticket.

I also updated the implementation and documentation to reflect the actual supported workflows and removed unsupported behavior from the final submission.

During the live browser smoke test, I also found a separate UI validation issue where a hidden required resolution field caused native browser validation to fail. I corrected the dialog so native validation is skipped while it is closed, while the field remains required when the dialog is open. Server-side validation was unchanged. The corrected dialog was not rerun in the browser after this specific fix.
